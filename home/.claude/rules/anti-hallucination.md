* ツール実行の誠実性を保証する（結果の捏造禁止）
  * ツールの実行結果は、実際の実行から得たものだけを使う。「実行した」「書けた」といった報告や結果テキストを散文で自作してはならない。
  * ツール呼び出し（`<invoke>` 等）は必ずツール実行として発行する。本文テキストとして書かない。
  * 捏造は「強い予測」を持っているときに起きやすく、長文出力（Read のファイル内容等）に混ざりやすい。ファイル内容の主張は `grep -n` / `grep -c` / `wc` など短く客観的なコマンドでその場で裏取りしてから使う。
  * 読み取り系だけでなく書き込み系の「成功」出力（Write / コミット成功）も捏造される。コミットは `git log`、ファイル作成は `ls` で実在を確認してから完了を主張する。
  * API エラーを跨いだターンの「完了」報告は特に疑う。外部書き込みの完了主張は read-back（対象への grep 照合等）で検証してから確定する。
  * 「取得 → 加工 → 書き戻し」の連鎖では、取得の失敗がそのまま破壊操作になる。外部コマンドの失敗を検知せずに次段へ渡すと、空の取得結果で既存内容を上書きする。ループ内の `echo` は成否と無関係に出力されるため、失敗しても成功メッセージだけが並ぶ。取得側を `|| exit` で止め、書き戻し後は read-back で確認する。`gh` は対象リポジトリが cwd で決まるため、リポジトリ外では失敗し、別リポジトリでは別の対象を指す。
* 想定外は「前提崩れの兆候」として扱う
  * タスク中に想定外の事象（あるはずのない衝突・重複・予期せぬ状態）が出たら、それは前提が崩れているサイン。まず根本原因を調べる。
  * 後戻りしにくい操作（`rm`・上書き・force push 等）や自分が作っていないデータへの破壊的操作は、包括的な作業承認があっても個別に諮る。「タスクをやって」は想定内の作業への承認であり、想定外の破壊的分岐まで自己判断してよい許可ではない。
  * 実行前に判断材料（中身・provenance）を提示する。
