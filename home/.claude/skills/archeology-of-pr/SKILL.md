# archeology-of-pr

過去の PR に埋まっているレビューのやり取りを掘り出し、**そのリポジトリでコードをレビューするときに読む規範** として蓄積する。

**なぜやるか**: レビュー指摘は「そのチームで実際に守られている決まり」の記録である。人が入れ替わっても PR の履歴には残り続けるが、誰も読み返さないので効かない。掘って規範の形にしておけば、次のレビューで先回りできる。

ユーザからの補足（あれば考慮する）: $ARGUMENTS

## 役割分担

このスキルは **掘って書き込む側**。生成物の `review-norms-from-pr` スキルが **レビュー時に読まれる側**。
両者は実行時に連携しない。生成物の冒頭に由来と更新方法を書き残すことで、読んだ人がこのスキルにたどり着けるようにする。

## プロセス

### 1. 対象と範囲を決める

- **対象リポジトリ**: 引数 `--repo` があればそれ。無ければ作業ディレクトリのリポジトリ（`gh repo view --json nameWithOwner -q .nameWithOwner`）。
- **掘削済み区間**: 対象リポジトリに `.claude/skills/review-norms-from-pr/SKILL.md` があれば、その冒頭の「掘削済み」行から区間を読む。
- **方向**:
  - 既定は新着方向。掘削済み区間の上端を `--after` に渡す。
  - 引数に `--back` があれば過去方向。区間の下端を `--before` に渡す。
  - 生成物が無ければ初回。範囲指定なしで新しい順に取る。
- **件数**: 引数 `--limit` があればそれ。無ければ 100。

### 2. 取得する

```bash
~/.claude/skills/archeology-of-pr/scripts/fetch-prs.sh \
  --repo <OWNER/NAME> --limit <N> [--after <PR>|--before <PR>] --out <一時ディレクトリ>
```

出力先は**対象リポジトリの外**（セッション用の一時ディレクトリ）にする。リポジトリを汚さないため。

スクリプトは PR ごとの Markdown と `manifest.md` を書き出す。各 PR には、レビューのスレッドごとに次が入る。

- 指摘が付いたコード断片と、その場所
- 指摘と返信の本文（発言者と、その人のリポジトリ上の立場つき）
- 解決済みかどうか、誰が解決したか
- 指摘後にそのコードが変わったかどうか、変わったならその差分

bot の発言はスクリプトが除外済み。人間の指摘が 1 件も無い PR も落ちている。

取得件数が 0 なら、走査した件数を報告してここで終わる。スキルは作らない。

### 3. 候補を抽出する（並列）

取得した PR を **25 件ずつ** に分け、`general-purpose` サブエージェントへ割り振る。分割数の上限は 6 体とし、PR が 150 件を超える場合は 1 体あたりの担当件数を増やして 6 体に収める。

各抽出役へ渡すもの:

- 担当する PR ファイルのパス一覧（本文は渡さない。サブエージェントが自分で読む）
- 下の「抽出役への指示」

抽出役は候補を**テキストで返す**。ファイルには書かせない。

#### 抽出役への指示

> 渡された PR ファイルを読み、レビュー指摘から「このリポジトリでコードを書くときの決まり」の候補を抜き出してください。
>
> 1 件ごとに次の形で、箇条書きで返してください。
>
> - **規範文**: 命令形の一文。特定の関数名・変数名・ファイル名を含めないこと。
> - **根拠**: PR 番号（複数あれば全部）
> - **対象領域**: エラー処理 / テスト / 命名 / 並行処理 など、短い語
> - **指摘の顛末**: 解決済みか、指摘後にコードが実際に変わったか
> - **元の指摘**: 原文の要点（1〜2 文）
>
> 落とすもの:
>
> - bot の指摘（既に除外されているはずだが、混じっていたら落とす）
> - typo・表記揺れの指摘
> - 反論されて引っ込み、コードも変わらなかった指摘
>   - ただし例外がある。反論の返信に「このリポジトリではこうする」という説明が付いている場合、**その説明文のほうが規範**なので拾うこと。
>
> 同じ趣旨の指摘が複数の PR にあれば、1 件にまとめて根拠の PR 番号を並べてください。
> 一般論に見えるものも、この時点では落とさずに拾ってください。選別は次の工程で行います。

### 4. 選別する（査読役 1 体）

`general-purpose` サブエージェントを 1 体立て、全抽出役の候補をまとめて渡す。査読役は対象リポジトリのコードを検索できる状態にしておく。

#### 査読役への指示

> 渡された候補を、次の 2 つの軸で仕分けてください。
>
> **第 1 軸 — このリポジトリの他の箇所でも成り立つか**
>
> 候補ごとに、**実際にリポジトリ内を検索して**、その規範を適用できる箇所が他にもあるか確かめてください。推測で判断しないこと。
> 適用先がその 1 箇所しか無ければ、**固有すぎる**ので捨てます。
>
> **第 2 軸 — このリポジトリを知らない人でも同じ結論にたどり着くか**
>
> - たどり着かない（このリポジトリを知らないと出てこない話）→ **規範**として採用。
> - たどり着く（その言語・その分野なら誰でも言う一般論）→ 規範には入れず、**「見落とされがちな観点」** へ回す。ただし 2 件以上の PR で言われたものだけを残し、1 件きりの一般論は捨てる。
>
> 返してほしいもの:
>
> 1. **規範**（採用）— 規範文 / 対象領域 / 根拠の PR 番号 / 第 1 軸で見つけた適用先の件数
> 2. **見落とされがちな観点** — 一文 / 言われた件数 / 根拠の PR 番号
> 3. **捨てたもの** — 規範文と、捨てた理由（固有すぎる / 一般論で 1 件きり / 対応されなかった）を一行ずつ

### 5. 書き込む

生成物は対象リポジトリの `.claude/skills/review-norms-from-pr/` に置く。
テンプレートは `assets/templates/review-norms-from-pr/` にある。

- **初回**: テンプレートをコピーし、`SKILL.md` の目次と `references/<領域>.md` を埋める。
- **2 回目以降**: 既存の内容に追記する。
  - 同じ趣旨の規範が既にあれば、**根拠の PR 番号を足して 1 件にまとめる**。規範文は書き換えない。
  - 既存と**逆のことを言っている**規範が出たら、自動で決めない。両方を並べて、どちらが現役かをユーザに尋ねる。
- `SKILL.md` 冒頭の「掘削済み」行を、今回の掘削で広がった区間に更新する。区間は 1 つに保ち、飛び飛びにしない。

**git への登録は自分で判断しない**。生成物を置いたことを報告し、コミットするかどうかはユーザに尋ねる。

### 6. 報告する

- 走査した PR 件数 / 人間の指摘があった PR 件数
- 採用した規範の件数、「見落とされがちな観点」の件数、捨てた件数と内訳
- 掘削済み区間が今回どう広がったか
- 生成物のパスと、git に登録するかの問い合わせ
- 矛盾する規範が見つかっていれば、その一覧と判断の依頼

## 判定基準の要点（迷ったときに戻る場所）

欲しいのは **「リポジトリ全体に効くが、このリポジトリを知らないと分からないこと」** だけ。
両端を落とす。片方だけの基準では、固有すぎる指摘か一般論のどちらかが必ず混ざる。

```
この repo 内の他の箇所でも成り立つ？（検索して確かめる）
  No  → 固有すぎ → 捨てる
  Yes ↓
この repo を知らない人でも同じ結論にたどり着く？
  Yes → 汎用すぎ → 「見落とされがちな観点」へ（2 件以上のときだけ）
  No  → 規範として採用
```
