# auto-pr-review

Pull Request を読み、指摘とマージ可否をまとめた HTML レポートを作る。

**なぜこの形か**: レビューの結論は「実際に読んだ範囲」でしか保証されない。ところが読んだ感覚は範囲より簡単に膨らむ。この手順は、範囲を worktree とコミット範囲で固定し、判定の前提をレポートに書き残し、別の目（外部エージェント）の指摘を裏取りしてから採る、の3点でその膨らみを抑える。

レビュー対象の PR: $ARGUMENTS

## 役割の置き方

**主レビュアーはこのセッション自身**。サブエージェントや外部エージェントに置き換えない。レポートを出したあとに人間のレビューへ付き添えるよう、読んだ内容をこのセッションに残すため。

外部エージェントは**反証役**として並行させる。返ってきた指摘はそのまま載せず、必ず自分で実コードに当たって確かめる。

## 0. 対象を確定する

引数から PR の URL を取る。無ければユーザに尋ねる。番号だけ・ブランチ名は受け付けない（どのリポジトリの話かが作業ディレクトリ依存になるため）。

URL から `<owner>/<repo>` と PR 番号を取り出す。

## 1. 古い worktree を片付ける

```bash
~/.claude/skills/auto-pr-review/scripts/cleanup-worktrees.sh <owner/repo> --keep <PR番号>
```

このスキルが作った worktree（`<PR番号>-auto-pr-review`）のうち、PR が閉じているものだけを消す。レポートと中間データは消さない。

**自分で実行する**。判断が入らない処理なので、サブエージェントを挟まない。削除という後戻りできない操作の結果を、要約を経由させずそのまま受け取るため。**`--force` を足さない** — 未保存の変更がある worktree を git が守れなくなる。

## 2. worktree を用意する

```bash
~/.claude/skills/auto-pr-review/scripts/prepare-worktree.sh <owner/repo> <PR番号>
```

PR の先端を detached HEAD で置き、レビュー範囲を `key=value` で返す。以降の手順はこの値を使う。

終了コードごとの対応:

| コード | 状況 | やること |
|---|---|---|
| 2 | ghq.root が未設定 | ここで終了し、ユーザに伝える |
| 3 | クローンが手元に無い | `ghq get <owner/repo>` を実行してよいかユーザに確認し、了承後に取得して再実行 |
| 4 | 既存の worktree に未保存の変更 | 止めてユーザに相談する（勝手に消さない） |
| 5 | git / gh の操作に失敗 | 出力を添えて報告し、原因を調べる |
| 6 | worktree の置き場所に、worktree ではないディレクトリがある | 止めてユーザに相談する（勝手に消さない） |

主な出力:

- `REPO_PATH` — メインのクローンの場所（手順 4 で外部エージェントの作業ディレクトリに使う）
- `WORKTREE_PATH` — レビュー対象のコードがある場所
- `HEAD_SHA` — PR の先端のコミット（中間データの `pr.head_sha` にそのまま入れる）
- `PREVIOUS_HEAD` — 前回レビュー時点のコミット（中間データの `run.previous_head`）
- `FULL_RANGE` — 取り込み先との共通祖先から PR の先端まで（PR 全体）
- `REVIEW_MODE` — `full`（全体）か `delta`（前回からの差分）
- `DELTA_RANGE` — `delta` のときの範囲
- `FALLBACK_REASON` — `full` に倒れた理由（初回 / 履歴が書き換えられた 等）
- `PREVIOUS_DATA` — 前回の中間データの控え（2 回目以降）
- `ROUND` — 今回が何回目か
- `REPORT_PATH` / `DATA_PATH` — 出力先

## 3. PR の位置づけを推定する

マージ可否は件数では決まらないので、何を基準に判断したかを先に固める。

PR の本文・ラベル・取り込み先ブランチ・下書きかどうかから、**どの段階の変更で、どこへ入るのか**を推定する。ユーザには尋ねない。推定した前提は、そのままレポートの総評に書く（前提が違えば読んだ人が気づけるように）。

## 4. 外部の攻撃的レビューを並行で起動する

起動する前に `external-agent-invocation` と `background-agent-ops` を読み、コマンドの形・落とし穴・見張りの仕込み方はそちらに従う。ここには固有の部分だけを書く。

- CLI は **codex**、**Adversarial Review モード**（まず反証を試みさせる）。
- **編集はさせない**（読むだけ）。レポートを書くのはこのセッションであり、コードを直す工程はこのスキルに無い。
- **作業ディレクトリはメインのクローン**（`REPO_PATH`）にする。worktree を作業ディレクトリにすると異常終了する既知の問題がある。
- 起動したら結果を待たず、手順 5 の自分のレビューへ進む。

指示文に必ず含めるもの:

```
【対象】
作業ディレクトリはメインの checkout で、レビュー対象はそこに入っていない。
対象は <WORKTREE_PATH> にあり、コミット範囲は <FULL_RANGE または DELTA_RANGE>。
索引やキャッシュではなく、`git log -p <範囲>` と実ファイルで実態を確認すること。

【この変更の位置づけ】
<手順 3 で推定した段階と行き先を 1〜3 行>

【重大度】
各指摘に Critical / Warning / Info を必ず付けること。定義は次のとおり。
- Critical: 取り込むと壊れる。どんな入力・状態で何が起きるかを必ず書く。
- Warning:  壊れはしないが、取り込む前に直したい。
- Info:     直さなくても取り込める。
Critical が一つも無い場合は「Critical なし」と明記すること。

【返し方】
指摘ごとに、場所（ファイルと行）・何が問題か・そう判断した根拠・直し方を書くこと。
```

**失敗・停止したら止まってユーザに相談する**。勝手に再実行も続行もしない。外部の目が入ったかどうかはレポートの信頼性に関わるため、黙って片肺で進めない。

## 5. 自分でレビューする

### 読むもの

レビューを始める前に、次を読む（無いものは飛ばす）。

1. 対象リポジトリの規約文書（`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` など）
2. 対象リポジトリに蓄積されたレビュー規範（`.claude/skills/review-norms-from-pr/`）
3. 変更箇所の周辺コード（呼び出し元、同じディレクトリの類似実装）
4. 変更されたファイルの言語に対応するレビュースキル
5. 変更箇所のドメインに対応するスキル

### 範囲

`REVIEW_MODE` に従う。

- `full` — `FULL_RANGE` の全体を見る。
- `delta` — `DELTA_RANGE` を見る。**加えて、前回の未解決の指摘の該当箇所は差分の外でも読み直す**（直ったかどうかを確かめるため）。

### 読み方

まず変更ファイルと行数の一覧を見て、自分で読み切れるかを判断する。読み切れないと判断したときだけ、`general-purpose` サブエージェントに**下調べだけ**を割り振る。

- サブエージェントに渡すのは「担当するファイルの範囲」と「変更の要約と、気になった箇所の位置を返せ」という指示。**指摘の採否は判断させない**。
- 返ってきた「気になった箇所」は、**自分でその箇所を読んでから**指摘にするかを決める。読まずに転記しない。

### 指摘を立てる

重大度は次で切る。

| 重大度 | 定義 | 必須 |
|---|---|---|
| Critical | 取り込むと壊れる（誤動作 / データ破壊 / 安全性 / 深刻な性能劣化） | どんな入力・状態で何が起きるかの筋書き |
| Warning | 壊れはしないが取り込む前に直したい（規約違反 / 設計の不整合 / テストの欠落） | — |
| Info | 直さなくても取り込める（好み / 将来の改善提案） | — |

**どう壊れるかを書けないものは Critical にしない**。書けない時点で、それは壊れる根拠が無いということ。

テストも静的解析も実行しない。読んで判断する。

## 6. 突き合わせる

自分の指摘を出し切ってから、この順で突き合わせる。先に読むと引っ張られる。

### 外部レビューの指摘

まだ終わっていなければ、ここで終わるまで待つ（`background-agent-ops` の見張りの仕込み方に従う）。待たずに先へ進むと、外部の目が入っていないレポートが入ったものと見分けられなくなる。

返ってきた指摘を**全件**、自分で実コードに当たって確かめる。

- 裏が取れたもの → 指摘に昇格させる（`source` を `codex` にする）。
- 裏が取れなかったもの → 指摘にはせず、**理由付きで不採用の一覧に残す**。

### PR に既に付いているコメント

```bash
gh pr view <PR番号> --repo <owner/repo> --json comments,reviews
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments
```

自分の指摘と重なるものには `already_reported` を付ける。専用の節は作らず、指摘ごとの印として残す。

### 前回の指摘（2 回目以降）

`PREVIOUS_DATA` の指摘を引き継ぎ、それぞれに状態を付ける。

- `resolved` — 直っていることを確かめられた
- `open` — まだ直っていない
- `new` — 今回はじめて出た指摘

## 7. 中間データを書く

`DATA_PATH` に JSON で書く。HTML は直接書かない。

```jsonc
{
  "pr": {
    "url": "https://github.com/owner/repo/pull/123",
    "number": 123,
    "repo": "owner/repo",
    "title": "PR のタイトル",
    "base_ref": "main",
    "head_sha": "<HEAD_SHA>",      // 次回の差分レビューの起点になる。必ず入れる
    "state": "OPEN"
  },
  "run": {
    "round": 1,                     // ROUND をそのまま
    "reviewed_at": "2026-09-17",
    "mode": "full",                 // REVIEW_MODE
    "range": "<FULL_RANGE か DELTA_RANGE>",
    "previous_head": null,
    "fallback_reason": "初回のレビュー",
    "scope_note": "下調べを分担した場合などの補足"
  },
  "overview": {
    "text": "この PR が何をしているかの説明",
    "files": {
      "added":    [{ "path": "a.ts", "additions": 120, "deletions": 0, "note": "任意の一言" }],
      "modified": [{ "path": "b.ts", "additions": 12, "deletions": 4 }],
      "removed":  [{ "path": "c.ts", "additions": 0, "deletions": 80 }]
    },
    "review_order": [
      { "path": "b.ts", "why": "この変更の中心。ここを読まないと他が理解できない" }
    ]
  },
  "verdict": {
    "decision": "merge",            // merge / conditional / block
    "headline": "一文での結論",
    "premise": "手順 3 で推定した位置づけ",
    "rationale": "件数ではなく、何を見てそう判断したか"
  },
  "findings": [
    {
      "severity": "critical",       // critical / warning / info
      "status": "new",              // new / open / resolved
      "first_round": 1,
      "title": "一文の要約",
      "file": "src/foo.ts",
      "line": "120-134",
      "detail": "何が問題か",
      "failure_scenario": "critical では必須。どんな入力・状態で何が起きるか",
      "evidence": "そう判断した根拠（規約文書・周辺コードの前例など）",
      "suggestion": "直し方",
      "source": "main",             // main / codex
      "already_reported": { "url": "https://...", "by": "レビュアー名" }
    }
  ],
  "external": {
    "status": "ok",                 // ok / failed / skipped
    "summary": "外部レビューが何を見て何を言ったか",
    "accepted": ["裏が取れて採用した指摘のタイトル"],
    "rejected": [{ "title": "...", "reason": "採用しなかった理由" }]
  },
  "other": [                        // 任意。どの節にも収まらない話だけを置く
    { "title": "小見出し（省いてよい）", "text": "自由記述" }
  ]
}
```

`other` は、指摘にも総評にも収まらないが伝えておきたいことを書く場所。例えば、この PR の責任ではないが同じ場所で繰り返し出そうな話、レビューで見きれなかった範囲、範囲外として扱った提案など。無理に埋めず、書くことが無ければ丸ごと省く。

散文の中では、バッククォートで囲んだ部分が等幅、`**` で囲んだ部分が太字になる。太字は一段落に一箇所までを目安にする（全部が太字だとどこも目立たない）。空行は段落の区切りになる。

マージ可否は件数で決めない。手順 3 の前提を踏まえた総合判断とし、`premise` と `rationale` の両方を埋める。

## 8. レポートを作る

```bash
python3 ~/.claude/skills/auto-pr-review/scripts/render-report.py \
  --data <DATA_PATH> --out <REPORT_PATH>
```

中間データに不備があれば、どこが足りないかを出して止まる。直して再実行する。

2 回目以降も出力先は同じ 1 枚。前回の中間データは手順 2 の時点で控えへ退避済みなので、必要になればそこから作り直せる。

**レポートは自動で開かない。** GitHub には一切書き込まない（コメントもレビューも投稿しない）。

## 9. 報告する

- マージ可否の判定と、その前提
- 重大度ごとの件数（解決済みを除く）
- 外部レビューの指摘のうち、採用した件数と不採用の件数
- 2 回目以降なら、前回から解決した件数と未解決の件数
- レポートのパスと worktree のパス
- 掃除で削除した件数と、消さずに残したものがあればその理由

スキルの仕事はここで終わり。指摘への対応をどう進めるかは、このあとの会話で決める。

## 付録: シェルから起動する

対話セッションを開かず、シェルから直接このスキルを始めるための入り口。

```bash
~/.claude/skills/auto-pr-review/extras/auto-pr-review.sh <PR の URL>
```

URL から PR 番号を取り出してセッション名にし、Claude Code をバックグラウンドで起動する（起動後は `claude agents` で一覧、`claude attach <id>` で合流できる）。

バックグラウンドでは、手順の途中でユーザに相談する場面（クローンが手元に無い・worktree に未保存の変更が残っている・外部レビューが失敗した）に答える人がいない。合流するまでそこで止まる。
